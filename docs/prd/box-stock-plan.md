> **상태: 계획만 세웠고 구현은 보류한다**(사용자 결정 2026-11-10). 요구사항은 [box-stock.md](box-stock.md), 선택의 이유는 [결정 로그](../decisions/2026-11-10-box-stock.md).
> 이 문서는 구현을 다시 시작할 때 맨땅에서 시작하지 않도록 **바뀔 파일과 방식, PR 순서, 위험**을 남긴 것이다. 구현 전에 아래 "재개 조건"을 확인하고 계획을 한 번 더 승인받는다.

## 재개 조건
1. 현장 시험(11/14~15)이 끝났다(시험 중 쌓인 사용량으로 기본값을 확인한다).
2. **박스 종류별 묶음당 장수**를 사용자가 어머니께 확인해 알려 줬다(입고·발주 입력이 묶음 단위라 PR 2부터 필요).
3. **확보 일수(5일치)에도 휴무일 지연을 더할지** 정했다(PR 3 알림 계산 전).
4. 현장 작업자 계정이 이 기능을 쓸 수 있도록 master가 권한을 부여할 준비가 됐다(자동 부여하지 않는다).

## 설계 방향 (기존 코드 재사용)
- **사용량**은 새로 만들지 않고 박스 리포트가 이미 쓰는 `packing_boxes`(제출한 박스) 집계를 재사용한다. 영업일 정의(박스가 제출된 날)와 요일 계산(`lib/reports/box-usage.ts`)도 그대로 쓴다.
- **재고·발주·입고는 이벤트로 쌓는다**(하나의 `box_stock_events` 테이블). 현재 재고는 이벤트를 접어서(fold) 계산하고 저장하지 않는다 → 정정은 "무효 처리 이벤트"로 하고 이력이 자동으로 남는다. 요구사항의 "수정·삭제 가능 + 이력 유지"와 맞는다.
- **묶음당 장수**는 박스 종류의 속성이라 `boxes` 테이블에 열(`bundle_size`)을 더하고 **기존 박스 관리 화면**에서 편집한다(별도 설정 화면을 만들지 않는다).
- **설정값**(알림 기준 일수·확보 일수·평균 영업일 수·주문 마감 시각·휴무일)은 기존 `app_settings`(`lib/app-settings.ts`)에 `boxStock` 키로 둔다. 변경은 master만.
- **발주 안내 글**은 기존 공유 방식(`use-share-text`, `share-text`)과 고객사 메시지(`lib/customer-message.ts`) 방식으로 순수 함수로 만든다.
- 계산은 전부 **순수 함수 + 단위 테스트**(`src/lib/stock/*`), 화면은 모바일 우선(`globals.css` 모바일 토큰), 새 테이블을 읽는 화면은 `rowsOrMissing` + `MIGRATION_OF_TABLE`로 마이그레이션 전에도 죽지 않게 한다(프로젝트 규칙).

## PR 순서 (동작하는 최소본에서 키운다)
각 PR은 하나씩 올리고 운영에서 확인한 뒤 다음으로 간다. 마이그레이션이 있는 PR은 "머지 전 SQL"에 적고 **SQL을 먼저 적용한 뒤 배포**한다.

### PR S1 — 실사 입력과 재고 현황 (장 단위, 알림 없음)
가장 작은 쓸모 있는 버전: 마감 후 실사를 남기고 추정 재고·재고 일수를 본다.
- **DB `0056_box_stock.sql`**: `box_stock_events`(`kind` 'count'|'order'|'receipt'|'void', `box_id`, `event_date`, `quantity`, `bundles`, `bundle_size`, `target_id`(무효 대상), `created_by`, `created_at`) + RLS(보기 `stock:view`, 쓰기 `stock:edit`, 수정·삭제 정책 없음 — 무효는 새 이벤트). 이 PR에서는 `count`와 `void`만 쓴다.
- **로직 `lib/stock/estimate.ts`(+테스트)**: 이벤트 접기(마지막 유효 실사), 제출 박스 사용량 차감, 소진 속도(14영업일 평균), 재고 일수, 상태(발주 필요/적정/과다는 PR 3), 음수 재고는 "입고 확인 필요"로.
  - **중요**: 차감 기준은 제출 시각이 아니라 **`order_date > 실사 기준일`인 제출 박스**다. `packing_records`는 재제출하면 지우고 다시 만들어 `submitted_at`이 바뀌므로, 시각을 기준으로 하면 실사 전에 낸 제출을 다시 낸 순간 이중 차감된다(요구사항: 이중 차감 금지).
  - 박스 종류는 `packing_boxes.box_id`로 매칭한다(이름은 바뀔 수 있음). `box_id`가 null(지운 박스)인 기록은 재고에서 빼고 화면에 건수를 알린다.
- **서버 로더 `lib/stock/server.ts`**: 이벤트·제출 박스·박스 종류를 읽어 위 로직에 넘긴다.
- **화면 `/stock`(새 메뉴 "박스 재고")**: 종류별 카드(추정 재고·재고 일수·마지막 실사 시각), **실사 입력**(종류별 숫자 → 추정과 하루 평균 사용량 이상 차이면 확인 → 저장), 실사 이력과 정정(무효 처리).
- **메뉴·권한**: `catalog.ts`에 `stock: { actions: { edit } }`, `dashboard-shell.tsx`에 메뉴 한 줄. 권한은 자동 부여하지 않는다 — master가 현장 작업자 계정에 부여한다.
- **테스트**: 접기, 사용량 차감, 재제출·삭제 시 재계산, 소진 속도(영업일 부족), 음수 재고, 같은 날 두 번 입력(마지막이 현재), 무효 처리.
- **규모**: 중간(마이그레이션 1, 로직 1, 화면 1).

### PR S2 — 입고와 발주 완료 기록 (묶음 단위)
- **DB `0057`**: `boxes.bundle_size integer`(null 허용, 양수 체크). `box_stock_events`에는 이미 `order`/`receipt`/`bundles`/`bundle_size` 자리가 있다(S1에서 만들어 둔다).
- **박스 관리 화면**: 종류별 묶음당 장수 입력(기존 `boxes-client.tsx`).
- **로직**: 입고 = 묶음 수 × 묶음 장수(발주·입고 시점의 장수를 이벤트에 복사해 나중에 장수를 바꿔도 이력이 변하지 않게), 도착 예정 = 발주 − 연결된 입고, **발주 수량 대비 입고 수량** 비교, 실사에서 추정보다 늘어난 만큼은 입고 입력 누락 후보로 표시.
- **화면**: 재고 화면에서 **입고 입력**·**발주 완료 입력**, 발주·입고 이력(정정 가능, 발주 대비 입고 표시).
- **테스트**: 묶음 환산, 장수 변경 후 이력 불변, 도착 예정 계산, 발주 대비 입고, 정정.
- **선행**: 묶음 장수 확정. **규모**: 중간.

### PR S3 — 설정과 알림 (휴무일 반영)
- **설정**: `app_settings.boxStock`(알림 기준 2, 확보 5, 평균 14, 마감 17:00, 휴무일 목록) 기본값·검증을 `app-settings.ts`에 추가, 설정 화면에 카드 하나(master).
- **로직 `lib/stock/alert.ts`(+테스트)**: **알림 기준 일수 = 기본 2일 + 발주·도착 사이에 낀 휴무일 수**(일요일 자동, 설정 휴무일 포함). 도착 예정일 계산은 "다음 영업일 마감 시각 전 발주 → 그다음 배송 가능일 도착". 단위 테스트로 고정할 사례: 월~목 저녁 2일치, 금·토 저녁 3일치(일요일 낌), 휴무일이 월요일이면 …, 휴무일이 연속(명절) 등.
- **화면**: 대시보드(overview)와 재고 화면 상단 알림 배너("물봉 발주 필요 — 17:00 전에 주문하면 내일 도착", "실사 필요"), 도착 예정분을 포함한 계산으로 중복 알림 방지.
- **선행**: 확보 일수에 휴무 지연을 더할지 결정(발주 수량 제안은 S4). **규모**: 중간.

### PR S4 — 발주 안내 (묶음 제안, 복사·공유)
- **로직 `lib/stock/order-suggestion.ts`(+테스트)**: 제안 = (확보 일수 × 소진 속도 − (추정 재고 + 도착 예정))을 묶음으로 올림, 0 이하면 제안하지 않음.
- **화면**: 발주 안내 글("물봉 3묶음, 선어박스 2묶음")을 만들어 복사·공유(기존 공유 방식), 안내에서 바로 "발주 완료" 입력으로 이어지게 한다.
- **선행**: 묶음 장수(S2에서 확보). **규모**: 작음.

### PR S5 — 박스 리포트 연동과 성공 지표
- 박스 리포트에 **재고 일수 추이**와 **성공 지표**(실사한 날 중 종류별 재고 일수가 2~7일치 범위인 날 비율)를 추가한다(`lib/reports/*`에 순수 함수 + 테스트). 목표 값은 운영 4주 측정 뒤에 사용자와 정한다.
- 실사 이력이 몇 주 쌓인 뒤에 의미가 있으므로 가장 마지막에 한다. **규모**: 작음~중간.

## 데이터 모델 초안 (구현 때 확정)
`box_stock_events`
| 열 | 설명 |
|---|---|
| `id uuid` | 기본키 |
| `kind text` | `count`(실사, 장 수) / `order`(발주 완료, 묶음) / `receipt`(입고, 묶음) / `void`(앞선 이벤트 무효) |
| `box_id uuid` | `boxes.id`(지운 박스는 set null → 화면에서 표시) |
| `event_date date` | 실사는 "이 실사가 반영하는 영업일 마감"의 날짜, 발주·입고는 발생일 |
| `quantity integer` | 실사: 남은 장 수 / 입고: 환산한 장 수 |
| `bundles integer`, `bundle_size integer` | 발주·입고의 묶음 수와 그때의 묶음당 장수(복사) |
| `target_id uuid` | `void`가 가리키는 이벤트, 입고가 연결되는 발주 |
| `created_by uuid`, `created_at timestamptz` | 입력자·시각(`default auth.uid()`, RLS `with check`로 본인만) |
- 같은 날 같은 종류 실사를 다시 입력하면 새 `count` 행이 쌓이고 **마지막 유효 행이 현재 값**이다.
- 인덱스: `(box_id, event_date)`, `(kind, event_date)`.

## 위험과 주의
- **재제출 이중 차감**: 위의 `order_date` 기준 규칙으로 막는다. 실사를 영업일 마감 **전**에 하면 그날 마감 이후 제출분을 놓칠 수 있다 → 화면에서 "마감 후 실사"를 안내하고, 마감 전에 한 실사는 그날 제출 박스를 다시 차감하지 않도록 `event_date`를 "반영한 영업일"로 입력받는다.
- **박스 종류 이름 변경·삭제**: `box_id`로만 매칭한다. 이름은 표시용이다.
- **휴무일 규칙의 복잡도**: 알림 기준·도착 예정일 계산은 가장 틀리기 쉬운 부분이라 S3에서 사례표를 테스트로 먼저 쓰고 구현한다.
- **알림은 화면을 열어야 보인다**: 외부 알림은 일부러 뺐다. 어머니가 앱을 거의 안 여는 경우 효과가 없다 → 4주 측정에서 확인하고 필요하면 카카오톡 알림톡을 별도 PR로 검토한다.
- **실사 부담**: 매일 6종 입력. 첫 4주 운영에서 입력 누락률을 보고 화면을 줄일 수 있는지 판단한다.
- **데이터 규모**: 박스 6종 × 영업일이라 작다. 14영업일 평균은 서버에서 계산하고 DB 함수는 만들지 않는다.
- **권한**: 새 권한 키(`stock:view`, `stock:edit`)는 사용자 권한 이관 마이그레이션을 두지 않고 master가 화면에서 부여한다(0045의 `has_perm` 방식으로 RLS 작성).

## 검증 계획
- 각 PR: `tsc`, `eslint`, `npm run build`, `npm test`. 순수 함수는 요구사항의 엣지 케이스를 사례표로 테스트한다.
- 운영 DB를 읽는 로컬 화면 확인(읽기 전용). 새 테이블에 쓰는 동작은 사용자 허용을 받은 뒤 테스트 기록을 남기고 지울 SQL을 같이 준다.
- 운영 데이터에 실사 이력이 쌓이기 전에는 재고·알림 값을 검증할 실제 데이터가 없으므로, 가짜 데이터 화면(커밋하지 않음)으로 모양과 계산을 확인하고 PR에 구분해서 적는다.
