# 주문 입력·주문 목록 연동 1단계 (2026-11-14 확정, 구현 대기)

배경: 형이 주문 입력에서 텍스트로 수정·삭제·미출고·취소를 입력해도 목록에 연동되지 않아 목록의 버튼을 쓰고 있다. 현장에서는 이 기능을 쓸 일이 없어서 가장 좋은 것은 입력과 목록이 정확히 연동되는 것이지만, **기술적으로 100% 보장할 수 없으면 목록의 버튼은 모두 유지**한다(사용자 기준). 감사 결과 100% 보장은 불가능하다고 판단했다: 입력 화면은 수량 수정·상품 추가·상품 취소·업체 전체 취소만 하고, 미출고·카드 삭제·상품 삭제·터미널/업체명/표시명 변경·포장방식 변경은 **아예 못 한다**. **목록의 수정·삭제·취소·미출고 버튼은 그대로 둔다.**

## 감사에서 나온 위험(주요)
1. 확정(`commitOrderLines`, `orders/actions.ts`)이 비트랜잭션: 취소·입력 이력을 먼저 저장하고 중간 실패 시 부분 반영, 카드만 남고 상품이 없는 경우, 재시도 시 새 줄 중복.
2. 이중 제출 방지가 버튼 비활성뿐: 더블탭·재시도·두 탭에서 같은 상품이 중복 추가.
3. 미리보기 판정을 확정이 그대로 신뢰: 그 사이 다른 사람이 바꾸면 중복 또는 덮어쓰기. 클라이언트가 보낸 `existingOrderItemId`의 소속도 검증하지 않음.
4. 줄 매칭이 허술: 상품명+포장방식만 보고 첫 1건을 쓰며(순서 임의), 사이즈·단위는 무시하고 덮어쓰고, 취소된 줄이 먼저 잡힐 수 있음.
5. 수정하면 "추가됨(new)"이 "수정됨"으로 사라짐. 입력의 "첫 입력" 판정(`isFirstInputOfDay`)이 날짜 기준 로그 수 + 로그 선기록이라 실패 후 재시도에서 어긋남.
6. 취소가 `orders:edit`만으로 가능해 목록의 `dashboard:delete` 분리를 우회(**사용자가 현재 방식 유지로 결정**).
7. 입력 쪽에 단위·무게·사이즈 길이·메모 길이·차수 검증이 없음.
8. 입력 후 `/overview`·`/packing-log`·`/scan` 즉시 갱신이 보장되지 않음.
9. 판정·매칭·상태 전이 단위 테스트 없음.

## 1단계 확정 범위 (마이그레이션 없음)
| # | 변경 |
|---|---|
| 1 | **확정할 때 현재 DB 상태로 줄을 다시 매칭**한다. 클라이언트가 보낸 상품 id는 믿지 않고 서버가 다시 찾는다. 같은 입력을 두 번 확정하면 두 번째는 "변경 없음"(멱등). |
| 2 | 계산을 먼저 끝내고 쓴다. **입력 이력은 맨 마지막**에 남긴다. 실패하면 무엇이 반영됐는지 오류 문구에 적는다. |
| 3 | 매칭: **살아 있는 줄 우선**(취소된 줄은 살아 있는 줄이 없을 때만 되살림). **같은 업체 카드에 같은 상품(같은 이름·포장방식)이 여러 줄이면 미리보기에서 막고 사람이 고르게 한다.**(결정 1) |
| 4 | 입력한 줄의 사이즈·단위가 기존 줄과 다르면 **덮어쓰되 미리보기에 "사이즈/단위가 바뀝니다(이전 → 이후)" 경고**를 표시한다.(결정 2) |
| 5 | **같은 붙여넣기 안에 같은 업체·같은 상품이 두 줄 이상이면 미리보기에서 막는다.**(결정 3) |
| 6 | 수정 시 상태 전이를 목록의 수동 수정 규칙(`manual-item-status.ts`)과 통일: 추가된 줄(new)은 수정해도 추가됨 유지. |
| 7 | 취소 권한은 **지금처럼 주문 입력 권한(`orders:edit`)만**으로 유지.(결정 4) |
| 8 | 목록이 쓰는 검증을 공용 함수(`order-validation.ts`)로 뽑아 입력·목록이 같은 규칙을 쓴다(단위 10자, 수량·무게 범위, 사이즈 100자, 메모 길이, 차수 1·2, 줄의 카드가 선택한 날짜·차수 소속인지 서버에서 확인). |
| 9 | 확정 후 갱신 대상을 목록 쪽과 같게 맞춘다(`/dashboard`, `/overview`, `/packing-log`, `/scan` 등). |
| 10 | 판정 로직을 순수 함수 `order-matching.ts`로 분리하고 단위 테스트 추가(같은 이름 여러 줄, 취소된 줄 우선, 사이즈 변경, 중복 입력, 상태 전이, 멱등). |

파일: `src/lib/order-matching.ts`(+테스트), `src/lib/order-validation.ts`, `orders/actions.ts`(미리보기·확정), `orders/new/new-order-client.tsx`(막힌 사유·경고 표시), `dashboard/actions.ts`(공용 검증 사용), 이 문서.

## 이번에 하지 않는 것
- **확정 전체를 DB 함수 한 번으로 묶는 원자화**(2단계, 마이그레이션 필요, SQL을 먼저 적용한 뒤 배포).
- **입력 문장으로 삭제·미출고·터미널 변경을 하는 새 문법**(3단계, 문법을 따로 정해야 함).
- **박스 재확인 경고에 사이즈·포장방식 반영**: 박스 기록에 그 값이 저장돼 있지 않아 기존 주문에 가짜 경고가 뜰 수 있어서 제외.
- 포장 체크된 줄의 수량을 바꿔도 포장 체크는 유지(현재의 "포장 후 변경" 소리 알림 설계).

## 검증과 한계
- 판정 로직은 단위 테스트. 미리보기(`suggestOrderLines`)는 읽기 전용이라 운영 DB에서도 화면 확인 가능.
- **확정(쓰기)은 운영 DB에 연결된 개발 서버로 시험하지 않는다.** 시험용 Supabase 프로젝트의 키(`.env.local`)가 있어야 확정 동작을 끝까지 확인할 수 있다. 없으면 확정 경로는 단위 테스트와 코드 검토까지만 하고 PR에 그렇게 적는다.
