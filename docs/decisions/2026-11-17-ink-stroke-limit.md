# 2026-11-17 칠판 필기 저장 개수 상한을 300에서 1000으로, 총 크기 상한 추가

## 맥락
`src/lib/ink/store.ts`의 `parseInkStrokes`는 `MAX_STROKES = 300`개만 남기고 **가장 오래된 획부터 버린다**. 서버 저장 전(`actions.ts`의 `saveBoardInk`)과 화면이 읽은 뒤(`board-ink-client.ts`의 `fetchBoardInk`)에 모두 이 함수를 지난다.
- 운영 데이터로 확인: 2026-11-16·11-17의 모니터 1·2 필기가 모두 **정확히 300개**였다. 상한에 걸려 있다는 뜻이다. 300개를 넘으면 오래된 필기부터 조용히 사라진다(아침에 어머니가 쓴 필기가 저녁에 없어짐). 화면에는 아무 안내가 없다.
- 지우개는 획을 조각내 새 획으로 저장하므로 개수가 더 빨리 찬다.
- 저장은 한 모니터의 획 전체를 서버 액션 한 번으로 보내고(마지막 저장이 남는 통째 덮어쓰기), Next 서버 액션 요청 본문 기본 한도는 1MB다. `next.config.ts`에 `serverActions.bodySizeLimit` 설정은 없다(기본값 그대로).
- 획 하나는 점이 최대 `MAX_POINTS` 800개다. 개수 상한만 올리면 긴 획이 많을 때 요청이 1MB를 넘어 저장이 통째로 실패할 수 있다. 참고로 기존 300획 상한에서도 800점짜리만 300개면 JSON 약 3MB(점당 약 7글자 기준)라 이미 1MB를 넘었다. 개수 상한만으로는 크기가 막히지 않았다.

## 결정
- `MAX_STROKES`를 **300 → 1000**으로 올린다.
- 총 크기 상한 `MAX_INK_BYTES = 700_000`(획 목록을 `JSON.stringify`한 글자 수)을 추가한다. 넘으면 **오래된 획부터** 버리고 순서는 유지하며, **가장 새 획(마지막)은 항상 남긴다**. 저장이 실패하는 것보다 오래된 필기를 버리는 편이 안전하다.
  - 700KB인 이유: 요청 본문 한도 1MB에서 서버 액션 인자(날짜·모니터)·직렬화 방식 차이·한글 등 2바이트 이상 글자 여유로 약 300KB를 남긴다. 획의 id·색·anchor는 ASCII라 글자 수와 바이트 수가 거의 같다.
- 구현: `limitInkStrokes(strokes, maxBytes = MAX_INK_BYTES)`(순수 함수, `store.ts`). 개수로 먼저 자른 뒤 **새 획부터** 한 획씩 직렬화해 합계가 상한을 넘는 획에서 멈춘다. 직렬화하는 양이 "남기는 양(최대 약 700KB) + 1획"으로 묶여, 입력이 아무리 커도 비용이 늘지 않는다. `parseInkStrokes`가 검증 뒤 이 함수를 부른다(저장 전·읽은 뒤 두 경로 모두).
- **화면(`ink-layer.tsx`)이 서버로 보내기 전에도 같은 함수로 자른다.** 서버가 자르는 것은 요청 본문이 이미 도착한 뒤라서, 화면 쪽 목록(칠판에서 한 세션 동안 계속 늘어남)이 커져 요청이 1MB를 넘으면 서버에 닿기 전에 실패한다. 보내는 쪽에서 자르면 요청 크기가 약 700KB로 묶인다. 화면의 그림 목록 자체는 줄이지 않는다(보이는 것은 그대로, 새로고침하면 서버 저장본 기준).
- 다른 모니터에서 복사해 온 획 id를 기억하는 localStorage 목록(`saveMigrated`)이 `slice(-600)`(= 2 × 300)이었다. 상한을 올렸으므로 `2 * MAX_STROKES`로 바꾼다. 그대로 두면 복사한 획이 600개를 넘을 때 오래된 id를 잊어, 그 획을 지웠어도 다음 복사 때 되살아난다.
- 바꾸지 않는 것: 필기 저장 형식, `lay`·`pts`의 의미, 줄·열 구조, 칠판 펜 입력·그리기, 서버 액션의 권한 검사. DB 변경 없음(마이그레이션 없음).

## 결과 (수치)
- 300획이 `pg_column_size`로 약 31KB(압축된 저장 크기, 획당 약 100바이트)였다. 1000획이면 압축 저장 약 100KB로 추정한다(선형 가정). **원본(`length(strokes::text)`) 크기는 확인하지 못했다.**
- 합성 데이터로 잰 원본 JSON: 30점짜리 획 1000개 약 463KB(획당 약 460글자). 이 정도는 크기 상한에 걸리지 않고 1000개 그대로 남는다. 100점짜리 1000개는 약 1.4MB라 크기 상한에 걸려 약 490개가 남고, 800점짜리 1000개는 약 11MB라 약 63개가 남는다(합성 데이터이며 실제 필기 분포가 아니다).
- `parseInkStrokes` 비용(이 PC의 Node, 합성 데이터, 20회 평균): 300획 약 1.5ms, 1000획(30점) 약 4ms, 최악 입력(1000획×800점, 11MB) 약 9ms. 칠판 브라우저는 이보다 느릴 수 있다(미측정).
- 읽기 경로: 화면의 15초 폴링은 먼저 `updated_at`만 읽고(`fetchBoardInkStamp`), 저장 시각이 달라졌을 때만 전체를 읽어 `parseInkStrokes`를 부른다. 그래서 폴링마다 파싱하지 않고, 변경이 있을 때만 위 비용이 든다.
- 그림 다시 그리기(`redraw`)와 지우개(`applyErase`)는 획 전체를 돈다. 선형이라 1000획×30점이면 점 3만 개 수준이지만, 칠판 기기에서의 속도는 확인하지 못했다.
- 되돌리기 기록(`HISTORY_LIMIT = 30`)은 이전 목록의 참조만 들고 있어 획이 늘어도 메모리가 크게 늘지 않는다. 이력 트리거(0067)의 점 수 급감(30%) 판정은 크기 상한으로 오래된 획이 잘려도 동작하며, 잘림으로 점 수가 크게 줄면 스냅샷이 한 번 더 남을 수 있다(해롭지 않다).

## 한계
- 상한(1000개 또는 약 700KB)에 가까워져도 화면에 안내는 없다. 넘으면 여전히 오래된 필기부터 조용히 사라진다. 상한이 3배 이상 커졌을 뿐이다.
- 두 모니터 합치기(`ink-layer`의 복사)로 한 모니터의 획이 상한을 넘으면 저장할 때 오래된 획이 잘린다(기존 동작과 같다).
- 칠판에서 필기가 많을 때의 그리기·지우개 속도는 확인하지 못했다.
- **이미 사라진 필기는 이 변경이 복구하지 않는다.** `board_ink_history`(0067, 7일 보관)에 이전 상태가 스냅샷으로 남아 있을 수 있어 일부 복구할 가능성은 있으나, 스냅샷은 설정 간격(기본 30분) 또는 점 수 30% 급감 때만 만들어져 상한 때문에 밀려난 획이 남아 있다는 보장은 없다. 이력 보기·복원 화면도 아직 없다.
- 구버전 화면(새로고침하지 않은 칠판·PC)은 옛 코드의 300개 상한으로 저장·읽기를 하므로, 배포 뒤 모든 화면을 새로고침하기 전까지는 300개로 잘릴 수 있다(저장 시 서버는 새 코드라 1000개까지 보관하지만, 구버전 화면이 읽어서 다시 저장하면 300개로 줄어든다).

## 배포 주의
- 영업이 끝난 뒤 배포한다. 배포 직전 `board_ink`를 CSV로 백업한다. 배포 뒤 칠판과 PC를 모두 새로고침한다(구버전 화면이 300개로 다시 저장하지 않게).
- 롤백은 안전하다: 옛 코드는 300개로 읽고 저장할 뿐 형식은 같다. 다만 롤백 뒤 옛 코드가 저장하면 그때 301번째 이전 획이 사라진다.

## 확인 방법 (배포 뒤)
```sql
-- 개수와 원본 크기. 개수가 1000, 원본이 700000 근처이면 상한에 걸린 것이다.
select order_date, monitor,
       jsonb_array_length(strokes) as stroke_count,
       length(strokes::text) as raw_chars,
       pg_column_size(strokes) as stored_bytes,
       updated_at
from board_ink
order by order_date desc, monitor;
```
- 칠판에서 300획을 넘기는 날 오후에도 아침 필기가 남아 있는지, `stroke_count`가 300을 넘는지 본다.
- 칠판에서 필기가 많을 때 그리기·지우개 속도와 저장 성공("저장 안 됨" 표시가 없는지)을 현장에서 확인한다.
- 원본 크기(`raw_chars`)가 실제로 어느 수준인지 관찰해, 700KB 상한이 너무 낮거나 높은지 판단한다.
