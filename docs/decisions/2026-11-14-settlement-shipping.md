# 정산 배송비(버스·퀵·택배) — 2026-11-14

## 문제
정산 때 고객사별로 버스·퀵·택배 비용을 붙여야 한다. 터미널마다 퀵이 안 되는 곳이 있고, 같은 터미널이어도 퀵을 쓰는 고객사와 아닌 고객사가 있다.
실제 정산 파일(형수님 엑셀)을 보면 버스는 박스당 1만 원으로 일정하지만, 퀵·택배는 고객사·날짜·박스 수에 비례하지 않는다.

## 결정
1. **별도 테이블 `settlement_shipping`(0062)**: 한 줄은 (그날 고객 카드 × 수단 `bus|quick|parcel`). 판매 줄(`settlement_sales`)에 넣지 않는다 — 품목 통계·이익률·매입내역 자동 행·업체별 매출이 오염되고, `settlement_sales`는 주문 줄 없이 행을 둘 수 없다.
2. **설정은 "제안"일 뿐이다**: 터미널 `quick_allowed`(퀵 가능), 고객사 `bus_rate/quick_rate/parcel_rate`(수단별 박스당 기본 금액, null이면 그 수단을 쓰지 않음). 정산은 출고 완료 카드마다 `박스 수 × 박스당 금액`으로 줄을 제안하고, 저장해야 확정된다. 날짜별 금액은 정산에서 직접 고친다.
3. **퀵 불가 터미널**: 그날 카드의 터미널(`daily_businesses.terminal_id`)이 기준이다(고객사 기본 터미널이 아니다). 퀵을 제안하지 않을 뿐, 이미 저장한 퀵은 지우지 않고 ⚠로 표시한다.
4. **영수증**: 저장한 배송비 줄(0원 제외)을 같은 `출고일|사업자|고객명` 묶음의 맨 뒤 품목 줄("버스 · 3박스")로 넣는다. 스냅샷 모양(version 1)은 바꾸지 않는다 — 배송비 줄이 기존 `ReceiptLine`에 그대로 들어가서 이미 발행한 영수증도 그대로 열린다. 판매 줄이 없는 고객의 배송비만으로는 영수증을 만들지 않는다. 15행 분할에는 배송비 줄도 센다. 단가는 금액이 박스 수로 나눠떨어질 때만 채운다.
5. **리포트는 건드리지 않는다**: `/reports/sales`의 매출·이익은 판매 줄만 쓴다. 배송비를 합산에 넣을지는 별도로 정한다.

## 알려진 한계
- 같은 날 1·2차 카드가 모두 출고되면 카드마다 배송비 줄이 따로 제안된다(필요 없는 줄은 "지우기").
- `/dispatch`(보내기) 고객사 탭의 합계는 아직 판매 줄만 더한다.
- 파일의 "운임" 줄(상자 단위)은 이번 범위에 넣지 않았다.
- 배송비를 영수증 발행 뒤에 고치면 이미 발행한 영수증은 그대로다(재발행 필요).

## 정산 날짜 단위
정산은 하루(출고일) 단위로 이뤄지므로 정산 화면의 주/월 단위(`?g=`)와 기간 선택, 여러 날일 때의 "출고일" 열을 없앴다. 정산 화면은 `?d=YYYY-MM-DD` 하루만 본다(기본 오늘). 기간별 집계는 리포트의 판매·수익에서 본다.

## 개정 (0063): 배송비 금액은 터미널에서, 고객사에는 사업자·퀵 이용만
정산이 복잡해지지 않게 설정 위치를 바꿨다.
- 배송비 기본 금액(박스당)은 **터미널**에서 정한다(`terminals.bus_rate/quick_rate/parcel_rate`). 켜진 수단의 금액만 입력한다: 택배 터미널(`is_parcel`)=택배, 그 밖=버스, 퀵 가능(`quick_allowed`) 터미널=퀵 추가. 고객사별 금액 열(0062의 `businesses.bus_rate` 등)은 쓰지 않아 삭제했다(입력된 값 없음을 확인).
- 고객사는 `uses_quick`(퀵 이용) 체크 하나만 둔다: 같은 퀵 가능 터미널이어도 퀵을 쓰는 고객사만 퀵을 제안한다. 규칙은 `ratesFor`(shipping.ts).
- 정산 배송비 = 카드 터미널의 박스당 금액 × 박스 수로 자동 산정. 날짜별로 고치고, 그날 쓰지 않은 수단은 "빼기"(0원으로 저장 → 영수증·합계에서 빠짐, "지우기"로 제안 복귀).
- 고객사에 `legal_name`(사업자명, 실제 법인·회사명)과 `seller_id`(사업자구분: 이 업체에 공급자로 쓰는 우리 사업자)를 추가했다. 사업자구분은 정산 판매내역·배송비·영수증의 사업자 구분 **기본값**이다(줄에 저장한 값이 있으면 그것이 우선). 줄에서 "미지정"을 고르면 고객사 기본값으로 돌아간다.
- 고객사 258곳의 사업자명·사업자구분 일괄 입력은 상호가 들어 있어 저장소에 두지 않는다(`.local-data/customer-import/`, gitignore). 확인용(읽기 전용)·적용용(트랜잭션) SQL을 Supabase에서 직접 실행한다.

## 엑셀 내보내기·가져오기 (하루치 통합 파일)
정산 화면의 "엑셀 내보내기"는 그날 판매·배송비·매입을 **한 파일 3시트**(판매 / 배송비 / 매입)로 내려받고, 노란 칸을 고쳐 "엑셀 가져오기"로 올리면 일괄 수정된다. 한 시트에 섞지 않은 이유: 판매는 주문 줄, 배송비는 (고객 카드 × 수단), 매입은 (출고일 × 품목) 단위라 행의 기준이 달라 섞으면 오히려 지저분해진다.
- **행 찾기**: 숨김 "키" 열(판매=주문 줄 id, 배송비=`카드id|수단`, 매입=`출고일|품목`). 품목·수량·단위는 원본과 같아지면 수정값을 지우고(null) 다르면 수정값으로 저장한다. 다른 날짜 파일은 숨김 "정보" 시트의 정산일로 막는다.
- **규칙**: 빈 칸 = 변경 없음, 삭제 없음, 판매·매입은 행 추가 불가(배송비만 맨 아래 빈 줄에 고객명·수단·배송비로 새 줄), 배송비 제안 줄은 값을 고쳤을 때만 저장, 단가·판매가 자동 연동 없이 파일 값 그대로 저장.
- **미리보기 → 적용**: 서버가 파일을 지금 DB 값과 견주어 변경 목록·오류를 보여 준다(저장 없음). 적용은 서버가 DB를 다시 읽어 계획을 새로 만들고(미리보기 값을 믿지 않는다), **오류가 하나라도 있으면 아무것도 저장하지 않는다**. 시트별로 따로 저장하므로 중간 실패 시 같은 파일을 다시 가져오면 남은 것만 저장한다(이미 반영된 칸은 변경 없음).
- 열이 다른 행을 한꺼번에 upsert하면 빠진 열이 null로 덮어써져서, 바뀐 열 묶음이 같은 행끼리 나눠 저장한다(`write.ts`).
- 권한은 `settlement:edit`(서버 확인). 내보내기는 보기 권한만 있어도 된다.
