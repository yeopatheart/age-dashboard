# 박스 할당 화면 UX 개편 (2026-11-14 결정)

요청: 어머니가 박스 할당할 때 박스가 3개를 넘으면 한 화면에 안 보여 스크롤이 많고 드래그 앤 드롭이 불편하다. 흐름을 자연스럽게 바꾸고, 할당이 끝나면 박스 종류별 필요 수량을 보여 달라. 현재 UI를 고수할 필요 없다.

## 진단 (1366×768, 운영 데이터 읽기 전용 실측)
- 히노츠키(박스 7개): 작업 영역 약 987px > 화면 768px. 이전 압축(2026-11-09-packing-log-compact)은 라벨 영역만 줄였고 박스 카드는 그대로였다.
- 박스 카드 3열 격자(카드마다 번호·종류·치수·상품이 세로로 쌓임) → 박스 4개부터 스크롤.
- 드래그는 화면 밖 박스까지 끌어야 하고, 끄는 동안 스크롤이 어렵다.
- 박스 추가 팔레트(종류 15개 이상)가 항상 2줄을 차지한다. 업체 목록과 작업 영역이 각각 스크롤된다.
- 업체 하나를 끝내는 클릭이 많다(추천 확인 → 수정 → 제출 → 다음 업체 선택).

## 확정한 결정
| 주제 | 고른 것 | 이유 |
|---|---|---|
| 사용 기기 | **PC + 마우스** | 어머니가 쓰는 환경. 버튼은 보통 크기, 드래그는 마우스용 보조로 남긴다 |
| 화면 방식 | **박스를 한 줄씩(행) 나열** | 박스 수가 늘어도 같은 구조. 7박스도 약 300px. 표 방식(행=상품·열=박스)은 하지 않는다 |
| 필요 수량 위치 | **박스 할당 화면 상단** | 어머니가 할당하면서 실시간으로 본다. 주문 목록·인쇄용 준비표는 이번에 하지 않는다 |

## 설계
1. **박스 행**: `번호 · 종류(드롭다운) · 상품 칩들 · +` 한 줄. 박스가 10개를 넘는 극단 경우만 목록 안에서 스크롤.
2. **탭으로 옮기기**: 상품 칩을 누르면 그 줄에 박스 번호 버튼(`1 2 4 새 박스`)이 나타나고 한 번 눌러 이동. 수량을 나눌 때는 같은 자리에서 숫자 입력. 드래그는 마우스용 보조로 유지.
3. **박스 추가**: 팔레트 2줄 대신 `+ 박스 추가` 한 개 → 종류 목록.
4. **업체 흐름**: `추천대로 제출하고 다음 업체` 한 버튼(추천이 맞는 업체는 클릭 한 번). 제출하면 다음 미완료 업체가 자동 선택. 업체 목록은 폭을 좁히고 남은 업체를 먼저 보여 준다(완료는 아래·흐리게).
5. **합포장을 같은 화면에서 설정**: 박스 행 아래 `1+2 묶기`. 이후 일괄 라벨 출력(PR C)의 전제다. 저장은 기존 `daily_businesses.merge_groups`(마이그레이션 불필요)에 제출과 함께 쓴다.
6. **오늘 필요한 박스**(화면 상단 줄): 박스 종류별 개수 + 합계 + `34곳 중 N곳 할당`. 제출한 업체는 제출 구성, 아직 제출 전인 업체는 추천 1순위 기준으로 합치되 구분해서(연한 색) 보여 준다. 기준은 `packing_boxes`(제출)와 추천 후보.

## 구현 접근과 순서
- 편집 영역(박스에 상품 담기·추천·제출)이 `packing-log-client.tsx`(892줄)의 목록·선택·DnD·draft 상태·헤더와 섞여 있다. 먼저 `PackingEditor`(업체 한 곳 + 박스 종류를 받는 컴포넌트)로 분리하고 그 위에 새 UX를 얹는다. 분리하면 주문 목록의 박스 열 클릭 → 박스 할당 팝업(PR B)도 같은 부품으로 가능하다.
- 업체 한 곳의 데이터만 읽는 로더(`loadPackingRows(supabase, date, onlyDailyId?)`)와, 팝업이 호출할 서버 액션(`getPackingEditorData`)이 필요하다. 추천 생성(`ensureRecommendations`)은 한 건씩 호출하도록 쪼갠다.
- 순서: ① 편집 영역 분리 + 새 UX(행 나열·탭 이동·필요 박스 줄·다음 업체) → ② 주문 목록 박스 열 팝업(분리한 부품 재사용) → ③ 합포장 설정과 일괄 라벨 출력(출력 순서는 이때 정한다).
- 검증 제약: 제출·이동은 운영 DB에 쓰기이므로 직접 누르지 않는다. 테스트 Supabase 프로젝트(.local-data/test-env)로 확인할 수 있는지 먼저 알아본다.

## 열린 질문 (구현 시작 때)
- 테스트 Supabase로 제출 흐름을 확인할 수 있는가(키가 로컬에 없어 사용자가 `.env.local`을 줘야 한다).
- 일괄 라벨 출력의 순서(업체 번호순 / 터미널순)는 PR C 시작 때 묻는다.

## 구현 결과 (1단계: 새 UX, 같은 날)
- **박스 행 나열**: 박스 카드 격자를 한 줄씩(`BoxRow`)으로 바꿨다. 한 줄 = 번호 · 종류 드롭다운(+물봉용 표시) · 상품 칩 · 빼기. 치수는 줄에서 빼고 툴팁으로 옮겼다. 1366×768, 히노츠키(박스 7개): 박스 영역 약 390px(이전 작업 영역 전체 987px), 박스 줄과 "박스 추가"까지 한 화면에 들어온다. 박스가 많으면 박스 목록 안에서만 스크롤(최대 36rem).
- **탭으로 옮기기**: 상품 칩을 누르면 박스 목록 위의 이동 줄(`MoveBar`)에 박스 번호 버튼·`새 박스…`·`빼기`가 나타나 한 번에 옮긴다. 아직 담지 않은 상품은 박스 목록 위 가로 칩 영역(`Pool`)에 있다. 담을 수량·실측 kg는 이동 줄에서 입력한다(예전에는 상품 칸에만 있었다). 드래그는 그대로 동작한다(마우스 드래그로 박스 줄 사이 이동 확인).
- **박스 추가**: 팔레트 2줄 → `+ 박스 추가…` 드롭다운 하나.
- **오늘 필요한 박스**: 화면 위 한 줄(`summarizeBoxNeeds`, `src/lib/packing/box-needs.ts`). 박스 종류별 개수 + 합계 + `N곳 중 M곳 제출`. 제출한 업체는 제출한 구성, 미제출 업체는 지금 화면의 구성(작성 중이면 그것, 아니면 보고 있는 추천)이며 미제출분이 섞이면 `제출 N`/`예상`으로 구분한다(운영 데이터에서는 미제출 업체가 상품 0개라 박스 추가로 확인).
- **제출하고 다음 업체**: 제출하면 다음 미제출 업체가 자동 선택된다(현재 업체 뒤쪽 우선, 없으면 처음부터, 모두 제출했으면 머문다). 업체 목록은 순서를 바꾸지 않고(작업 중 위치가 흔들리지 않게) 제출한 업체만 흐리게 한다.
- **계획과 달라진 것**: 편집 영역을 `PackingEditor`로 분리하는 일은 이 단계에서 하지 않았다(화면 안에서 컴포넌트만 교체). 주문 목록의 박스 열 팝업(2단계)에서 재사용할 때 분리한다.
- **합포장 설정·일괄 라벨 출력은 3단계**로 남아 있다.
- **검증**: tsc·lint 통과, 테스트 329개(집계 3개 추가). 브라우저: 칩 클릭→이동 줄→번호로 이동, 빼기, 새 박스에 담기, 마우스 드래그 이동, 빈 박스 제출 차단 유지, 박스 추가 시 필요 수량 줄 갱신. 제출(운영 DB 쓰기)은 눌러 보지 않았다.
