# 2026-11-16 칠판 필기 서버 이력(스냅샷)

> 일부 대체됨(2026-11-18): 정기 스냅샷은 시계 기준(pg_cron)으로 바뀌고 요약이 늘었다. `2026-11-18-board-ink-history-v2.md`를 먼저 본다.

## 문제
칠판 필기는 중요한 기록(어느 고객사의 어느 상품에 몇 마리·몇 kg 포장했는지)인데, 스마트칠판 정전식 터치 때문에 쉽게 그려지거나 지워지고, 펜이 켜진 채 다른 작업자가 손을 대는 일이 있다. `board_ink`는 저장할 때마다 행 전체를 덮어써서 지워진 필기는 서버 어디에도 남지 않는다.

## 결정 (사용자 확정: B안, 간격은 설정 가능·기본 30분, 보관 7일)
- 화면 캡처가 아니라 **획 JSON 이력**을 남긴다. 캡처는 칠판 기기에서 라이브러리를 돌려야 해 칠판 펜 장애 직후라 위험하고, 복원이 안 되고, Storage를 새로 써야 한다.
- 주문은 UPDATE·DELETE로 덮어써져 이력이 없고, 필기는 줄·칸에 붙어(anchor = `daily_businesses.id` / `order_items.id`) 저장되므로, 필기만 보관하면 나중에 "무엇을 가리켰는지" 읽을 수 없다. 그래서 스냅샷에 **그 시점의 줄 요약**(업체 카드·상품 줄·수량·단위·사이즈·취소·포장 체크)을 같이 복사한다.
- `board_ink` AFTER UPDATE 트리거(`0067_board_ink_history.sql`)가 덮어쓰기 직전 상태(OLD)를 `board_ink_history`에 남긴다. DB 안에서 끝나므로 앱 코드 변경·왕복이 없고 칠판 렌더 경로를 건드리지 않는다.
  - 남기는 때: (1) 같은 날짜·모니터의 마지막 스냅샷이 설정 간격(`app_settings.boardInkSnapshotMinutes`, 기본 30, 5~240)보다 오래됐을 때, (2) 점 수가 직전 저장보다 30% 이상 줄었을 때(최소 1분 간격). 점 수 = 모든 획의 좌표 쌍 개수. 획 수는 지우개가 획을 쪼개면 늘 수 있어 쓰지 않는다.
  - 비어 있던 상태·내용이 같은 저장은 남기지 않는다. 보관은 7일(스냅샷을 만들 때 같은 트리거에서 삭제, cron 없음).
- **이력 실패가 칠판 저장을 막지 않는다**: 트리거 전체를 예외 처리로 감싸 경고만 남긴다. 요약만 실패하면 요약만 비우고 필기는 남긴다. 즉시 끄기: `drop trigger if exists board_ink_history_snapshot on public.board_ink;` (재배포 불필요).
- 설정 키는 기존 관례대로 `AppSettings` 필드명(`boardInkSnapshotMinutes`)이다. `saveSettings`가 모든 필드를 키 단위로 저장하므로 저장 로직은 바꾸지 않았다. 설정이 없으면 트리거가 기본 30분을 쓴다(그래서 SQL만 먼저 적용해도 된다).
- Realtime 발행에는 넣지 않는다.

## 알려진 한계
- **작은 오터치는 최대 간격(기본 30분)만큼의 필기를 잃을 수 있다.** 30% 급감은 크게 쓸었거나 전체 지우기일 때만 잡는다. 숫자 한두 자를 지우거나, 지우개로 천천히 조금씩 지우면 저장 한 번당 변화가 작아 급감으로 안 잡힌다. 간격을 줄이면 낮출 수 있다.
- 요약 시점이 어긋날 수 있다: 스냅샷의 strokes는 직전 저장본(OLD)이지만 요약은 스냅샷을 만드는 지금의 주문 상태다. 펜을 계속 쓰는 중이면 시차는 몇 초지만, 한참 쉬었다 쓰면 그 사이 주문이 바뀐 경우 어긋난다(`strokes_saved_at`이 OLD 저장 시각).
- 모니터 1·2 배정은 화면이 계산하므로 요약은 `sort_order` 순서의 전체 목록이다.
- 같은 날짜·모니터 행을 동시에 쓰면 마지막 저장이 남는 기존 한계는 그대로다.
- **이력 보기·복원 화면은 아직 없다.** 지금은 SQL로 `board_ink_history`를 읽어야 한다. 모니터 분할이 클라이언트 계산이고 줄 밖 낙서가 화면 레이아웃에 의존해서, 별도 화면으로 재현하기보다 기존 칠판 읽기 전용 렌더링을 스냅샷 데이터로 재사용할 수 있는지부터 조사해야 한다. 복원은 칠판이 열려 있으면 다음 저장 때 자기 상태로 덮어쓰므로 칠판 새로고침 안내가 필요하다.

## 검증 (이 PC, 로컬 Postgres = pglite 0.5.16, Supabase 미접속)
- Supabase 환경을 흉내 낸 스키마(역할 anon/authenticated, RLS, `has_perm`, 기본 권한)에서 58개 항목 통과: 재적용 멱등, 요약 내용·정렬, 간격 경과, 급감(20/25% 안 잡힘·33% 잡힘·전체 지우기), 1분 최소 간격, 빈 상태·같은 내용, 설정값 보정(범위·문자열·객체·소수·없음), **이력 실패 격리 4종(요약 실패·INSERT 실패·이력 테이블 없음·설정 테이블 없음에서도 저장 성공)**, 7일 보관, 권한(사용자는 이력 쓰기·트리거 직접 호출 불가, 권한 없으면 0건), search_path 고정, 모니터 `s1~s9`, board_ink 삭제와 무관.
- 최악 상한(300획×800점) 스냅샷 1건은 압축 저장 약 150KB(jsonb 텍스트 약 1.7MB). 저장 1회당 트리거 추가 비용은 이 크기에서 약 40ms(WASM 측정이라 참고치, 실제 Postgres는 더 빠를 것으로 추정하나 미측정).
- 단위 테스트 514 통과(`app-settings.test.ts` 신규), tsc·lint·build 통과. 설정 화면 입력 검증(3·241·7.5·빈 값은 저장 막힘, 5·30·45·240은 가능)을 브라우저에서 확인, 새 탭 콘솔 오류 0건.
- **테스트 Supabase(`tyglkx…`) 실측(사용자가 0067을 SQL Editor로 적용한 뒤, 서버 키로 실제 PostgREST 호출) 19개 항목 통과**: 첫 UPDATE에서 스냅샷(OLD 5획·50점)과 그날 업체 카드 11개 요약(번호·업체명·상품·수량·단위·상태·포장), 30분 안에서는 추가 없음, 전체 지우기에서 급감 스냅샷, 저장은 항상 성공, 설정 10분(9분 경과 안 생성·11분 경과 생성), anon은 이력 읽기·쓰기·트리거 함수 호출 모두 불가. 테스트 행·이력·설정은 모두 삭제해 원래 상태로 돌렸다.
- **미확인**: 로그인한 사용자(JWT)의 실제 칠판 펜 저장 경로(서버 키는 RLS를 우회하므로 사용자 권한 경로는 로컬 Postgres로만 확인), 운영 데이터 크기, 설정 저장 버튼 흐름(누르지 않음), 운영 DB 적용.
