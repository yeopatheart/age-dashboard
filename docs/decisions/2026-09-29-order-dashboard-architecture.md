# 2026-09-29 — 주문 대시보드 아키텍처 결정

`/idea-interview`로 진행한 인터뷰에서 확정한 선택들. 각 항목은 "선택지 → 고른 것 → 이유" 순서.

## 1. 실측 중량/사이즈 입력 방식

- 선택지: (a) 빔 프로젝터+화이트보드, (b) TV에 보드마카로 직접 기재, (c) 종이 시트 자동 재출력, (d) 음성 입력, (e) 블루투스 무선 저울, (f) 재사용 write-erase 아크릴 카드
- 고른 것: (f) 재사용 아크릴 카드 — 코드(업체번호-상품순서) + 실측값만 적어서 일괄 촬영 후 OCR
- 이유:
  - (a) 작업장이 밝아 빔 프로젝터 가시성 문제
  - (b) 소금기로 인한 전자제품(TV) 손상 위험 + 정산에 실제 측정값 필요(단순 완료 표시로는 부족)
  - (c) 사용자가 명시적으로 거부 — 작업자 손이 젖어 있어 종이가 못 버팀, 주문 변동이 너무 잦음
  - (d) 사용자가 명시적으로 거부 — 주변 소음이 심함
  - (e) 기존 저울도 물/염분 환경에서 자주 고장나는 실측 이력이 있어, 무선 전자장비 추가는 오히려 고장 위험을 늘림. 또한 측정값-업체 매핑 문제를 별도로 풀어야 함
  - (f) 저전력/저기술이라 습한 환경에 강하고, 코드로 식별하므로 위치 의존성이 없음

## 2. 카드-TV 물리적 부착 방식

- 선택지: (A) 재사용 젤 패드로 TV 화면에 직접 부착, (B) TV는 건드리지 않고 별도 트레이에 모아서 일괄 촬영 + 화면 색상으로 완료 표시
- 고른 것: (B)
- 이유: TV 화면에 아무것도 붙이지 않아 손상 위험이 원천적으로 없고, "완료 표시"라는 시각적 효과는 카드 인식 직후 화면 색상 전환으로 동일하게 얻을 수 있음

## 3. 카드-주문 줄 매핑 번호 체계

- 선택지: (A) 전체 순번(flat, 카카오 메시지 도착 순), (B) 업체번호-상품순서 계층 코드(예: "12-2")
- 고른 것: (B)
- 이유: 업체 수가 하루 50개 내외로 작아 업체 번호가 항상 작은 수로 유지되고, 상품 순서도 그 업체 내에서만 세므로 숫자가 항상 짧음. 대시보드 기존 디자인(`order-biz-card` 단위 그룹핑)에 업체 헤더 뱃지 1개 + 줄마다 작은 순번 뱃지로 자연스럽게 얹을 수 있음(레이아웃 재설계 불필요, Explore 서브에이전트로 확인함)

## 4. 카카오 메시지의 신규/수정 구분 방식

- 선택지: (초안) 메시지 텍스트 자체에 번호+"-수정"/"-취소" 키워드를 형이 직접 써서 보냄, (최종) 시스템이 업체명을 오늘자 기존 주문과 자동 대조해 줄 단위로 신규/업데이트를 제안하고 사람이 확인
- 고른 것: 최종안
- 이유: 실제로는 카카오 메시지에 별도 주문번호가 없고, 형이 이전 번호를 기억해서 재사용한다는 전제 자체가 불확실함. 또한 신규 주문과 기존 주문 수정이 한 메시지에 섞여 오는 경우가 실제로 있어, 사람이 미리 모드를 나눠 붙여넣기보다 시스템이 줄 단위로 제안하고 사람이 검토하는 편이 더 견고함(파싱 실패 처리와 동일한 "AI 제안 → 사람 확인" 패턴 재사용)

## 5. 박스 포장 추천 데이터 소스

- 선택지: (a) 처음부터 수동 입력으로 시작 후 점진적 학습, (b) 기존 엑셀/장부+화이트보드 사진 기반 학습, (c) 어머니 인터뷰로 규칙 추출, (b)+(c) 병행
- 고른 것: (b)+(c) 병행
- 이유: 실사용 기록(엑셀/장부, 최근 몇 개월치)이 이미 존재해 처음부터 학습 데이터로 쓸 수 있고, 데이터에 없는 예외적 판단은 어머니 인터뷰로 보완하는 것이 가장 현실적

## 6. 섀도우 모드 정확도 측정 기준

- 선택지: (A) 별도의 실시간 캡처 절차를 새로 만들어 어머니의 실제 선택을 기록, (B) 형이 이미 엑셀로 정리해온 기존 기록을 그대로 비교 기준(ground truth)으로 재사용
- 고른 것: (B)
- 이유: 이미 존재하는 습관/절차를 그대로 활용해 별도의 캡처 인프라를 새로 만들 필요가 없음

## 7. Supabase 프로젝트 분리 여부

- 선택지: (A) age-seafood와 같은 Supabase 프로젝트 공유, (B) 별도 Supabase 프로젝트
- 고른 것: (B)
- 이유: 두 시스템(주문·포장 대시보드 vs 터미널 송장 대사)의 스키마를 분리해 마이그레이션 리스크와 RLS 복잡도를 낮춤. 자동 대조 연동이 필요해지더라도 Supabase가 프로젝트마다 REST API(PostgREST)를 자동 제공하므로, 분리로 인한 향후 연동 비용 증가는 제한적(핵심 난이도는 매칭 로직이며 이는 DB 통합 여부와 무관하게 동일하게 필요함). 무료 티어가 조직당 최대 2개 프로젝트까지 허용해 비용 문제도 없음

## 8. 인증/권한 수준

- 선택지: (A) 개인별 로그인 + 접근 기록(감사 추적)만, (B) 역할별 데이터 가시성 제한(RBAC)
- 고른 것: (A)
- 이유: 과거 직원의 유사 업종 창업 사례로 인해 접근 추적은 필요하지만, 현장 작업자 전원이 업무상 오늘 주문 전체를 볼 필요가 있어 역할별로 가릴 수 있는 데이터 경계가 뚜렷하지 않음. B는 구현 비용 대비 실익이 낮다고 판단

## 9. 프로젝트 위치 및 이름

- 선택지: `apps/`(제품) vs `sandbox/`(실험)
- 고른 것: `apps/age-dashboard` (기존 `~/Desktop/store automation`에서 이전, package.json name도 `age-dashboard`로 변경)
- 이유: 가족 사업에 실제로 쓰일 도구로, age-seafood와 동일하게 제품 범주에 해당
