# 별도 주문 업체번호를 일반 주문과 따로 발급 (2026-11-13)

## 문제
11/13 주문 목록에서 38번(스시카이키) 다음 번호가 54번(뱅해이네)으로 건너뛰었다(형이 문제로 제기). 원인: 업체번호를 날짜당 카운터 하나(`order_day_counters`)로 발급해서, 별도 주문(택배·직배송 등 `terminals.is_separate`) 카드가 39~53을 쓰고 이후 일반 주문이 54부터 이어 붙었다. 주문 목록은 별도 주문을 빼고 보여 주므로 번호가 끊겨 보인다.

## 결정
- 번호 범위를 나눠 따로 발급한다: **일반 주문 1~500, 별도 주문 501~999**. 사용자가 선택(2026-11-13).
- 1번부터 따로 세지 않는 이유: 번호는 박스 라벨 QR의 `업체번호 3자리`(`src/lib/labels/barcode.ts`)에 들어가고 DB에서 하루 안에 유일해야 한다(`unique (order_date, business_number)`). 별도 주문도 라벨을 출력하므로 두 시리즈가 같은 번호를 쓰면 스캔이 섞인다.
- 선택하지 않은 안: 별도 주문 101번부터(일반 주문이 하루 100개를 넘으면 막힌다. 11/13이 55번이었다).
- 어느 카운터를 쓸지는 **카드를 만드는 시점의 터미널 `is_separate`**로 정한다. 터미널이 없는 카드는 일반 주문. 나중에 터미널의 별도 주문 설정을 바꿔도 이미 발급된 번호는 그대로다.
- 한도를 넘으면 오류를 낸다(일반 501째, 별도 1000째). 번호를 조용히 0으로 대체하던 `?? 0` 폴백은 없앴다.

## 바뀐 것
- `supabase/migrations/0056_separate_business_number.sql`: `order_day_counters.next_separate_number`(기본 501), `assign_separate_business_number(date)` 추가, `assign_business_number`에 500 초과 검사 추가.
- `src/lib/business-lookup.ts`: `separateTerminalIds`, `assignBusinessNumber`. `orders/actions.ts`(카카오 붙여넣기 확정)와 `findOrCreateDailyBusiness`(새 주문 추가)가 사용.
- 테스트 `src/lib/business-number.test.ts`.

## 일부러 하지 않은 것
- **이미 발급된 번호는 바꾸지 않는다.** 11/13의 39~53(별도)과 54·55는 그대로이고 그날 목록의 점프는 남는다. 번호가 출력한 라벨 QR에 박혀 있어 바꾸면 스캔이 안 될 수 있다.
- 표시용 재번호(화면에서만 1,2,3으로 다시 세기): 화면 번호와 라벨 번호가 달라지면 현장 혼선이 생겨 2026-11-09(PR #111)에 "화면 번호 = 라벨 번호"로 맞춘 결정과 충돌한다.

## 배포 순서
SQL(0056)을 먼저 적용하고 코드를 배포한다. 0056은 컬럼·함수 추가뿐이라 옛 코드도 적용 직후 정상 동작한다(옛 코드는 별도 주문도 일반 번호로 발급한다).

## 확인하지 못한 것
- SQL을 실제 DB에서 실행해 보지 못했다(이 환경에서 마이그레이션을 적용할 수단이 없다). 단위 테스트는 RPC 이름 선택과 오류 처리만 검증한다.
- 별도 주문 팝업·박스 할당·스캔 화면에서 5xx 번호가 어떻게 보이는지는 브라우저로 확인하지 않았다(코드상 번호를 그대로 표시).
