# 2026-11-20 고객사 간 합포장 (서로 다른 두 고객의 각 1박스를 한 박스로)

## 배경
기존 합포장(`merge_groups`, 2026-10-30)은 한 고객 카드 안의 박스 여러 개를 함께 테이핑하는 것이다. 현장에는 서로 다른 두 고객의 각 1박스를 한 박스로 합쳐 내보내는 경우가 있다. 터미널 박스 수가 줄고, 상차 스캔은 두 고객 가운데 한 곳의 QR만 하고, 퀵기사에게는 "받으면 분리해서 각각 배송"을 요청한다. 합포장 여부는 현장의 어머니가 박스 크기를 보고 **포장 뒤에** 정하므로, 주문 입력 순서로는 붙어 있지 않을 수 있다.

## 결정 (사용자 확정 2026-11-20)
- **두 고객에게 버스비·퀵비를 각각 청구한다.** 그래서 정산(운임·영수증)은 바꾸지 않는다. 연결은 터미널 박스 수·상차 스캔·퀵기사 글에만 쓴다.
- **라벨은 바꾸지 않는다.** 합포장은 라벨을 붙인 뒤에 정하고, 각 박스에 자기 라벨이 붙어 있어야 헷갈리지 않는다. 연결하면 둘 중 하나만 스캔해도 두 박스가 상차된다(PR2).
- **박스 단위가 아니라 카드 단위 연결.** 합포장은 2곳만, 각 고객 1박스일 때만. 두 고객의 터미널은 같아야 한다.
- **연결 방법(주문 목록, 칠판 터치):** 고객명을 꾹 누르면(0.5초) 연결 대기가 시작되고, 다른 고객명을 탭하면 **바로 연결**된다(확인 없음). 연결 직후 10초 동안 "되돌리기"가 뜬다. 연결된 고객명을 꾹 누르면 "합포장 연결을 취소할까요?" 확인창이 뜨고 [연결 취소]를 눌러야 풀린다.
- **칠판 두 대(모니터 1·2가 다른 기기)는 대기 상태를 공유한다.** Supabase Realtime broadcast(임시 메시지)로 나누고 DB에는 저장하지 않는다. 30초가 지나면 대기가 사라진다. 한 기기 안에서는 broadcast가 없어도 동작한다.
- **표시:** 묶음마다 색과 글자(A, B…)를 준다. 두 줄의 번호 칸 왼쪽에 색 띠, 박스 칸에 "합A" 배지. 배지를 누르면 아래에 "합A: 스시렌 ↔ 스시쿄세이"가 4초 뜬다. 줄 높이·칸 구성은 바꾸지 않는다(필기는 줄에 붙어 있어 줄 높이를 바꾸면 어긋난다). 연결 대기 중에는 연결할 수 없는 고객명이 흐려진다.
- **터미널 박스 수 칩:** 쌍은 한 박스로 센다(`getTerminalBoxTotals`).

## 저장 구조 (0072)
- `daily_businesses.box_link_id`: 짝 카드의 id. **양쪽 카드가 서로를 가리킨다.** 카드가 지워지면 짝의 연결도 풀린다(`on delete set null`). 박스를 다시 제출해도 카드는 유지돼 연결도 유지된다.
- 연결·해제는 DB 함수 `link_box_pair(a, b)`·`unlink_box_pair(id)`로만 한다. 두 카드를 한 번에 바꾸고(id 순서로 잠가 동시 연결 충돌을 막는다) 조건을 DB에서도 확인한다: 같은 날짜·같은 터미널(택배 제외), 서로 다른 카드, 아직 연결되지 않음, 제출한 박스가 각각 1개, 모든 주문이 취소된 카드가 아님, 상차된 박스가 없음. 위반하면 한국어 사유로 예외를 낸다.
- 이미 실시간 구독 중인 `daily_businesses`를 쓰므로 연결·해제가 두 칠판에 바로 반영된다(별도 publication 등록 없음).
- 박스를 다시 제출해 박스 수가 1이 아니게 되거나 박스 기록을 지우면 연결을 자동으로 푼다(`packing-log/actions.ts`). 이때 화면 안내는 없다(칠판의 배지가 사라진다).

## PR2: 상차 스캔 전파·퀵기사 글 (사용자 확정 2026-11-20)
- **스캔 전파(양방향):** 한쪽 라벨을 스캔하면 짝 고객의 박스(1번)도 함께 상차한다(`scan/actions.ts`). 스캔 되돌리기도 짝을 함께 되돌린다. 이력(`box_label_events`)에는 짝의 박스도 scan/undo로 남는다. 짝의 주문이 모두 취소됐으면 짝은 상차하지 않는다. 짝의 라벨이 아직 없으면(출력 전) 함께 상차하지 못하고, 스캔 결과에 "짝의 라벨이 아직 없어 함께 상차되지 않았습니다" 경고를 띄운다.
- **합계는 쌍을 한 박스로 센다:** 상차 스캔 화면의 터미널별·전체 합계, 보내기 화면의 터미널 상차/전체 박스(`linkedCounts`). 업체 카드 목록은 업체별 그대로(각 0/1·1/1). 둘 다 상차돼야 한 쌍이 "상차"로 센다.
- **퀵기사 글(터미널당 N쌍 가능):** 합계 줄 뒤에 합포장 안내 줄 한 줄과 묶음 줄(쌍마다 `· 고객1 + 고객2`)이 붙는다. 업체별 줄에는 합포장 고객 뒤에 " (합포장)"(변수 `{합포장표시}`). 합계는 실제 싣는 박스 수. 쌍이 아직 상차 전이면 업체별 줄·합계에 넣지 않고 미상차 줄에 `고객1 + 고객2 1박스`로 한 덩이로 올린다. 한쪽만 상차돼 있어도 쌍은 아직 상차 전으로 본다. 합포장이 없는 터미널의 글은 이전과 똑같다.
  ```
  11/20(금) 남부 상차 완료
  스시렌 1박스 (합포장)
  스시쿄세이 1박스 (합포장)
  스시시류 1박스
  합계 2박스
  ※ 합포장 1건 (합계는 합포장을 1박스로 센 수입니다). 받으시면 분리해서 각각 배송 부탁드립니다
  · 스시렌 + 스시쿄세이
  ```
- **문구 설정:** 설정 화면의 상차 완료 글에 줄 종류 두 개(합포장 안내 줄, 합포장 묶음 줄)를 추가했다. 줄을 비우면 그 줄은 글에서 빠진다.
- **저장된 업체별 줄 문구가 있으면** 새 기본값(`{고객사명} {박스수}박스{합포장표시}`)이 적용되지 않는다(저장된 값이 우선). "(합포장)" 표시를 쓰려면 설정 > 상차 완료 글 > 업체별 줄에 `{합포장표시}`를 붙여 저장해야 한다. 안내 줄·묶음 줄은 저장된 문구와 상관없이 나온다.
- 마이그레이션 없음(PR1의 0072만 필요). PR1이 먼저 머지·적용돼야 한다.
- 검증: 단위 테스트(글 구조 N쌍·상차 전·한쪽만·짝이 목록에 없음·합포장 없음·문구 변경, 합계, 스캔 되돌리기 문구), 테스트 DB+로컬 서버 — 쌍 A↔B 스캔 시 B도 상차(양방향), 상차 현황 1/3(5곳이 3박스), 두 쌍+단독 1곳 글(합계 3박스·묶음 줄 2개), 되돌리기가 짝까지 되돌림, 짝 라벨이 없을 때 경고, 설정 화면 새 줄·미리보기. 칠판은 건드리지 않음.

## 이전 PR(PR1)에서 하지 않은 것 (PR2에서 처리)
- 상차 스캔 전파(한쪽 스캔 → 짝 박스도 상차), 스캔 화면 합계, 퀵기사 글의 합포장 문구와 합계(실제 싣는 박스 수).
- 대시보드 현황(`overview`)·리포트의 터미널 박스 수는 바꾸지 않는다.
- 휴대폰 카드 화면·별도 주문 팝업에는 꾹 누르기·배지를 넣지 않았다(칠판·PC 주문 목록만).
- **PR1만 배포한 상태에서는 연결해도 스캔은 각 박스를 따로 요구한다.** PR2가 나갈 때까지 현장 안내가 필요하면 연결 기능 사용을 미루는 것도 방법이다.

## 위험·한계
- 새 열을 읽는 화면이라 **0072를 먼저 적용하지 않고 배포하면 주문 목록이 열리지 않는다**(`select`에 `box_link_id`가 들어 있다). 적용 순서: SQL 먼저, 코드 배포는 그다음.
- 꾹 누르기는 눈에 보이지 않는 기능이다. 처음에는 현장에 알려야 한다.
- 칠판에서의 꾹 누르기·두 칠판 사이 broadcast는 PC로는 확인할 수 없다(칠판 확인 필요). broadcast는 Supabase Realtime의 공개 채널을 쓰므로, 프로젝트에서 "공개 채널 허용"이 꺼져 있으면 두 칠판 사이 공유만 동작하지 않는다(한 기기 안에서는 동작).
- 펜이 켜져 있으면 고객명 칸이 읽기 전용이라 연결할 수 없다(펜을 끄고 연결).
- 연결 대기 상태는 같은 날짜를 보고 있는 모든 화면(PC 포함)에 보인다.

## 검증
- 단위 테스트(`box-link.test.ts` 6개, `orders.test.ts` 1개 추가), tsc·린트·`npm test` 631개 통과.
- DB 함수: 로컬 Postgres(pglite) 27항목 통과 — 정상 연결, 양방향 중복 연결 거절, 실패 시 변화 없음, 해제(어느 쪽이든)·재연결·카드 삭제 시 해제, 날짜·터미널·박스 수·박스 기록 없음·취소·상차·택배 거절, 주문 없는 카드·일부 취소 카드 허용, 자기 자신 제약, 권한(anon 거부), 재적용 멱등.
- 화면(테스트 DB에 0072 적용, 로컬 서버, 브라우저 탭 2개): 꾹 누르기 → 연결 대기 시작(꾹 누르고 뗄 때 주문 패널은 열리지 않음), 박스 2개 고객·다른 터미널 고객은 흐려짐, 연결 불가 고객을 탭하면 사유 안내(대기 유지), 먼저 고른 고객을 다시 탭하면 대기 종료, 짝을 탭하면 바로 연결(두 줄 "합A"·색 띠, 터미널 박스 수 5→4), "되돌리기"로 해제, 연결된 고객 꾹 누르기(어느 쪽이든) → 확인창 → [닫기]는 유지·[연결 취소]는 두 카드 함께 해제(칩 4→5), 일반 탭은 주문 패널을 연다, 대기는 30초 뒤 사라진다.
- **탭 2개 사이 공유:** 한 탭에서 꾹 누르면 다른 탭에 같은 안내줄이 뜨고 취소도 전달된다. 다른 탭에서 짝을 탭해 연결하면 시작한 탭의 안내줄이 사라지고 배지가 나타난다(이 테스트 프로젝트에서는 공개 채널 허용). 운영 프로젝트의 공개 채널 설정은 확인하지 못했다.
- **줄 높이:** 연결된 줄과 연결 안 된 줄의 높이가 같다(필기 위치에 영향 없음). 이 화면의 줄 높이는 줄 수와 상관없이 기준 화면 규칙으로 18px 고정이라, 줄이 5개일 때와 35개일 때 모두 같은 단계에서 점검했다.
- **글자 점검(`scripts/text-clip-audit.js`):** 새 "합A" 배지는 잘림·기준선 정렬·세로 중앙 모두 위반 0. 잘림 점검에는 표 머리 칸 4건("터미널"·"고객명"·"박스"·"상품 1", 1.2~1.3px)이 나오는데, 연결 전후로 똑같고 머리 칸 코드는 이 PR이 바꾸지 않았다(이 확인 환경의 영향일 수 있다. main에서 따로 재 보지는 않았다).
- **확인하지 못한 것:** 칠판 터치로 꾹 누르기, 칠판 두 대 사이 공유, 박스 재제출·박스 기록 삭제 시 자동 해제(코드 한 줄+DB 함수는 검증, 화면 경로는 미확인).
