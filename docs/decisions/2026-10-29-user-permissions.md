# 사용자 및 권한 (2026-10-29)

이전 결정(2026-09-29, 결정 8)은 "로그인한 사람은 모두 같은 데이터를 읽고 쓴다(역할 구분 없음)"였다. 계정이 늘고 현장 작업자(상차 스캔 등)가 생기면서 메뉴·기능별로 나눈다.

## 결정
- **master 계정은 `master@ageseafood.com` 하나**(코드 상수 `MASTER_EMAIL`). 모든 메뉴·기능을 쓰고, **"사용자 및 권한" 메뉴(`/users`)는 이 계정만** 열 수 있다. DB를 읽지 않고 이메일로 판단하므로 권한 표에 문제가 있어도 master는 들어올 수 있다.
- **권한 키는 `메뉴:동작`**(`src/lib/permissions/catalog.ts`가 단일 출처). 모든 메뉴에 `view`(메뉴 열기)가 있고, 동작은 대부분 `edit`/`delete`, 일부만 별도 키: 박스 할당(제출·삭제·라벨 출력), 상차 스캔(스캔·되돌리기). 동작 권한을 주면 `view`가 같이 붙는다. 44개 server action을 개별로 켜고 끄는 방식은 화면이 길어지고 기능이 늘 때마다 목록을 같이 고쳐야 해서 쓰지 않았다.
- **새 사용자는 권한 없음으로 시작**한다. 권한이 하나도 없으면 `/no-access`로 간다.
- **저장**: `user_permissions(user_id, permissions text[])`(0031). RLS는 본인 행 읽기만 허용하고 쓰기 정책이 없다 — 변경은 서버의 `service_role` 키로만 한다.
- **확인은 앱 서버에서만**: 모든 `page.tsx` 맨 위 `requireMenu`, 모든 server action 맨 위 `requirePermission`(숨긴 버튼만 믿지 않는다). 화면의 버튼 숨김·비활성은 `useCan()`으로 한다. DB 규칙(RLS)은 여전히 "로그인했으면 전부 허용"이라, 로그인한 사용자가 Supabase API를 직접 호출하면 우회할 수 있다. 필요해지면 테이블별 RLS를 나중에 추가한다.
- **사용자 등록은 master가 이메일+비밀번호(8자 이상)로 직접** 만든다(`auth.admin.createUser`, 이메일 인증 생략). 공개 회원가입은 열지 않는다. 삭제도 같은 메뉴에서 한다(본인·master는 삭제 불가).
- `SUPABASE_SERVICE_ROLE_KEY`는 서버 전용 환경변수(`NEXT_PUBLIC_` 없음). `src/lib/supabase/admin.ts`만 쓴다.

## 알려진 한계
- 권한을 바꾼 직후 그 사용자의 열린 화면은 새로고침해야 반영된다(서버 확인은 다음 요청부터 바로 적용된다).
- 읽기(조회) 서버 함수는 `getOrderHistory`처럼 일부만 확인한다. 페이지 자체는 `requireMenu`로 막는다.
- 기능 권한 화면 숨김은 주요 버튼 위주다. 빠진 버튼이 있어도 서버가 막아 오류로 끝난다.
