# 2026-11-18 칠판 필기 이력 v2 (시계 기준 스냅샷 + 표 재현용 요약)

## 문제
`2026-11-16-board-ink-history.md`의 이력(0067)은 필기 JSON과 줄 요약을 남기지만 이력을 눈으로 볼 화면이 없다. 주문이 자주 바뀌어서, 이력 화면이 **그 시점의 칠판 표를 그대로 다시 그려야** 필기의 의미가 읽힌다. 0067 구조로는 두 가지가 막혔다.
1. 요약에 표를 그릴 값이 모자란다(터미널·박스 수·메모·합포장·미출고·물봉·기포기·상품 id·색 등).
2. 스냅샷이 "직전 저장본 필기 + 지금 주문 요약"이라 둘의 시각이 달라서, 주문이 바뀌면 필기와 요약이 어긋난다.

## 결정 (사용자 확정 2026-11-18: 화면 정확도 b안, 별도 주문 a안, 시점 차이 b안, 급감 트리거 유지)
- **정기 스냅샷을 시계 기준으로 바꾼다.** pg_cron이 5분마다 `board_ink_snapshot_tick()`을 부르고, 그 순간의 현재 필기와 현재 요약을 한꺼번에 읽어 남긴다(0068, 등록은 0069). 간격은 기존 설정 `boardInkSnapshotMinutes`(기본 30분, 5~240분)를 쓴다. 5분 주기라 실제 간격은 설정값 이상이고 가장 가까운 5분 단위로 올림된다(30초 여유).
  - 남기는 조건: 필기가 비어 있지 않고, 마지막 스냅샷 이후 저장이 있었고, 마지막 스냅샷과 내용이 다르고, 간격이 지났을 때. 최근 2일 안에 저장된 행만 본다.
- **점 수 급감 트리거는 남긴다.** 오터치·지우개·전체 지우기 직전 상태를 `drop`으로 남기는 안전망이다. 시계 기준만으로는 30분 사이의 급한 손실을 못 잡기 때문이다.
  - 급감을 알아볼 수 있게 `prev_point_count`·`new_point_count`(직전·직후 점 수)를 같이 기록하고 `reason = 'drop'`으로 구분한다. 이력 화면이 이 값으로 "급감 감지" 표시를 한다.
  - 이 스냅샷은 필기가 직전 저장본, 요약이 지금이라 시점이 어긋날 수 있다(`strokes_saved_at` = 필기 저장 시각). 화면이 어긋남 가능성을 같이 알린다.
  - drop은 같은 날짜·모니터의 직전 drop과 1분 이상 떨어져 있을 때만 만든다(0067은 모든 스냅샷과 비교해서 정기 스냅샷 직후의 급감을 놓칠 수 있었다).
- **요약을 v2로 늘린다**(`summary_version` 2). 업체: 터미널·별도 주문·택배 여부, 메모, 합포장, 박스 수, 업체 id, 기본 이름. 상품: 상품 id, 미출고 수량·사유, 보조 중량, 물봉, 기포기, 기준 수량·단위. 정렬은 화면과 같게 `sort_order`, 같으면 발급 번호순이다. `meta`에는 그 시점의 터미널 색, 그날 주문에 나온 상품 색, 그날 강조 상품을 담는다(주문 화면은 이것들을 현재 값으로 읽기 때문에 따로 남겨야 이력에서 색이 어긋나지 않는다).
- 0067 때 쌓인 이력은 `summary_version` 1(옛 형식)로 남고 표로 재현하지 못한다. 7일 보관이 지나면 사라진다.

## 알려진 한계
- **"박스 변경" 작은 배지는 이력 표에서 빠진다.** 제출 기록·추천 서명·"이름만 바뀐 경우 제외"를 앱이 계산하는 값이라 SQL로 옮기지 않았다.
- 정기 스냅샷은 "저장이 있었던 행"만 남긴다. 필기는 그대로고 주문만 바뀐 시간은 새 스냅샷이 없다(필기가 같으면 마지막 스냅샷과 요약이 같은 필기를 가리킨다).
- 30분 사이에 쓰고 지운 필기는 정기 스냅샷으로 못 잡고, 점 수가 30% 이상 줄어든 저장만 drop으로 잡는다(0067과 같은 한계).
- 5분 주기라 설정 간격보다 최대 5분 늦게 남을 수 있다.

## 적용 순서
1. 테스트 Supabase에서 `0068` → `0069`를 이어서 적용하고(0068만 적용하면 그 사이 정기 스냅샷이 끊긴다) `cron.job`·`cron.job_run_details`와 이력 행을 확인한다.
2. 같은 순서로 운영 SQL Editor에 적용한다. 앱 코드 변경은 없고, 앱은 이 테이블을 아직 읽지 않으므로 칠판·PC 화면은 그대로다.
3. 이력 화면(`/dashboard/history`)은 이후 PR이다.
- 되돌리기: `select cron.unschedule('board_ink_snapshot_tick');`(정기 중지), `drop trigger if exists board_ink_history_snapshot on public.board_ink;`(drop 중지). 재배포 불필요.

## 검증
- 로컬 Postgres(pglite 0.5.16, Supabase 흉내 스키마)에서 65항목 통과(3회 반복): 재적용 멱등, 0067 이력 행이 v1로 남음, 요약 v2의 필드·정렬·박스 수 규칙(택배 1, 기록 없음 null)·날짜 필터, meta(터미널 전체·사용 상품만·강조 순서), 정기 스냅샷의 조건(간격 안/밖, 설정 10·3→5·999→240·잘못된 값→30, 같은 내용 재저장, 빈 필기, 2일 지난 행, 모니터별·날짜별 요약), 요약 실패 시에도 필기는 남김, 7일 보관, drop(20% 감소 제외·정확히 30%·전체 지우기·1분 제한·정기 스냅샷 직후·빈 상태), 이력 테이블이 없어도 칠판 저장 성공, 권한(조회는 `dashboard:view`, 쓰기·함수 호출 불가). 하네스는 저장소에 두지 않았다(pglite가 `package.json`에 없다).
- **미확인**: pg_cron 등록·실행(0069)은 pglite에서 검증할 수 없다. 테스트 Supabase에서 확인해야 한다. 실제 Supabase에서 로그인 사용자(JWT) 경로의 펜 저장 시 drop 트리거 동작, 운영 데이터 크기는 확인하지 못했다.
