# 실시간 첫 구독이 조용히 죽는 문제 (2026-11-09)

## 증상
E2E 점검(테스트 Supabase)에서, 주문 목록 PC 화면을 **새로고침한 직후** 칠판 모드(실시간 알림)의 첫 구독은 칩이 "실시간"인데도 `postgres_changes` 이벤트가 한 건도 오지 않았다(5분 안전 새로고침 전까지 화면이 안 바뀜). 같은 탭에서 칠판 모드를 껐다 켜서 **재구독**하면 정상이었다. 브라우저를 거치지 않은 Node 클라이언트(같은 키, 로그인 후 구독)는 정상이라 DB 발행(0041)·RLS 문제가 아니다.

## 측정 방법
새로고침 → 7초 대기 → 다른 클라이언트에서 값이 같은 no-op UPDATE → 5초 뒤 콜백에 도착한 이벤트 수를 센다(임시 계측, 커밋하지 않음). 화면 갱신 횟수(`_rsc` 요청)는 하네스의 탭 숨김/보임 깜빡임 때문에 오염되어 기준으로 쓰지 않았다.

| 실험 | 결과(이벤트 수) |
|---|---|
| 수정 전 (StrictMode 켬) | 0 |
| E0: `reactStrictMode: false` | 0 → StrictMode는 원인이 아님 |
| E1: 구독 전에 `await supabase.realtime.setAuth()`, 채널 이름을 매번 다르게, 재연결은 제거 완료 후 | 3회 모두 1 (정상) |

## 결정
E1을 적용한다(`src/lib/realtime/use-live-refresh.ts`). E1의 두 요소(토큰 먼저 / 채널 이름 갱신) 중 어느 쪽이 결정적인지는 따로 가르지 않았다. 둘 다 코드에 있던 잠재 레이스를 없앤다.
- 안전 새로고침을 5분 → 1분(탭이 보이는 동안만), 낡은 화면 표시(`STALE_MS`)를 10분 → 3분으로 줄였다.
- 모바일 주문 목록은 실시간·소리가 없으므로 30초마다(보이는 동안) 새로 받는다(`useAutoRefresh`).

## 확인하지 못한 것
- 운영(기존 anon 키, `next start`)에서 같은 증상이 있었는지. 테스트 프로젝트는 새 publishable 키를 쓴다. 배포 뒤 같은 절차로 한 번 확인한다.
- 소리·음성은 청취하지 못했다(목록의 "변경 N건"으로 이벤트 생성만 확인).
