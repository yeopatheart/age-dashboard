# 성능 계측 (2026-11-20)

## 왜
"느리다"는 체감과 개발 Mac에서 잰 값뿐이라, 칠판 TV·PC·폰에서 실제로 얼마나 걸리는지, 개선(#227 칩 맞춤 등)이 얼마나 먹혔는지 숫자로 볼 수 없었다.
칠판에서는 개발자 도구를 열기 어렵다. 측정 방식은 사용자가 (b) 자체 경량 계측으로 결정했다(수동 / 자체 경량 / 외부 서비스 중).

## 무엇을 재나 (사용자 확정 항목 그대로)
| metric | 정의 | value_ms / extra_ms |
|---|---|---|
| `load_block` | 화면이 열린 뒤 10초 안의 멈춤. 처음 열기는 페이지 시작부터, 메뉴 이동은 이동을 시작한 순간부터. 다른 화면으로 가거나 창이 가려지면 그때까지 | 가장 길게 멈춘 시간 / 멈춘 시간 합계 |
| `nav` | 메뉴·링크를 누른 순간부터 새 경로가 반영되고 두 프레임이 지날 때까지 | 걸린 시간 |
| `refresh` | 실시간 갱신(`useLiveRefresh`의 router.refresh transition) 시작부터 끝까지 | 걸린 시간 |

각 기록에 화면 이름(`:id`로 묶음), 모니터(주문 목록만 1·2·all), 터치 여부, OS 종류, 창 크기, 배포 버전(커밋 7자리, 로컬은 `local`), 멈춤을 잰 방식(`loaf`/`longtask`)을 붙인다. 고객명·주문 내용은 담지 않는다.
멈춤은 `long-animation-frame`으로 재고, 없는 브라우저는 `longtask`로 잰다(`blockingDuration` 대신 50ms를 뺀 값). 둘 다 없으면 `load_block`은 남기지 않는다(나머지 둘은 그대로).

## 어떻게
- 브라우저(`src/instrumentation-client.ts` → `src/lib/perf-client.ts`)가 모아서 **1분마다·창이 가려질 때** `/api/perf`로 묶어 보낸다(한 번에 최대 40건, 버퍼 200건, 실패한 묶음은 버리고 연속 3번 실패하면 그 화면에서는 멈춘다). 로그인 화면에서는 기록하지 않는다.
- `src/app/api/perf/route.ts`가 검증(`src/lib/perf-payload.ts`: 허용 목록·범위, 잘못된 기록은 건너뜀)하고 `perf_events`에 넣는다. 로그인 사용자의 세션으로 넣는다(RLS: authenticated insert만, 조회는 `settings:view`). 서비스 키는 쓰지 않는다.
- 14일이 지난 기록은 저장 요청이 올 때 **시간당 한 번** `purge_perf_events()`로 지운다. pg_cron은 쓰지 않는다(환경 차이·설정 부담).
- **끄기 스위치**: `app_settings`의 `perfEnabled`가 `false`면 서버가 저장을 멈추고 `{enabled:false}`로 답해 기기도 보내기를 멈춘다(서버 캐시 60초 + 기기는 다음 전송 때). 설정 화면 버튼은 없고 SQL로 한다(0073 머리말).
- 조회는 화면 없이 `docs/perf-queries.sql`을 Supabase SQL Editor에서 실행한다(운영 DB는 Claude가 접근하지 못해, 결과를 붙여넣어 해석한다).

## 알고 가는 것
- 직원 계정이면 누구나 `/api/perf`에 저장할 수 있다. 요청당 40건·본문 32KB 제한만 있고 기기별 호출 제한은 없다(악의적 반복은 막지 못한다). 기록이 업무 데이터가 아니라 영향은 용량뿐이고, 14일 뒤 지워진다.
- 메뉴 이동(`nav`)은 경로가 바뀔 때만 잰다. 주문 목록의 날짜·모니터 전환(쿼리만 바뀜)은 `nav`로 안 남고, `load_block`(새 화면 시작)만 남는다.
- 탭이 가려졌다 다시 보일 때는 새 화면으로 세지 않는다(가려질 때 열린 화면의 기록을 확정하고 끝).
- 서버 쪽 시간(응답·쿼리)은 이 계측에 없다. 필요하면 다음 단계에서 추가한다.
- 칠판 Chrome의 버전을 몰라 `api` 열로 어떤 방식으로 쟀는지 남긴다.

## 검증 (2026-11-20, 이 Mac, 운영 빌드, 테스트 DB에 0073 적용)
- 단위 테스트: 입력 검증·멈춤 요약·모으기/보내기 19개(전체 665개 통과). `0073`은 pglite 20항목(적용·재적용, 로그인 사용자는 저장만 되고 읽기·수정·삭제 불가, CHECK 거절, 14일 삭제, 로그인 전 거절).
- 실제 흐름: 주문 목록 열기 → 메뉴 이동 → 실시간 갱신 → 페이지를 벗어나며 전송. `perf_events`에 `load_block`·`nav`·`refresh`가 모두 쌓였다(예: 열릴 때 가장 긴 멈춤 0.23~0.49초, 갱신 0.55~0.99초, 메뉴 이동 29ms — 70줄 시드, `build=local`, `api=loaf`).
- 끄기 스위치(`perfEnabled=false`): 서버가 `{enabled:false}`로 답하고 저장하지 않음. 다시 켜면(캐시 60초 뒤) 저장됨.
- 잘못된 요청: 깨진 JSON 400, 형식 오류·41건 400, 33KB 초과 413, 잘못된 기록은 건너뛰고 나머지 저장. 로그인 없이 호출하면 `/login`으로 307.
- 영향 없음: 계측을 켠 상태에서 칩 값 해시가 #227 검증 때와 같고(모니터 1·2·전체 249·229·478칩), 화면 멈춤도 비슷하다(모니터 1 0.83+0.28초, 모니터 2 1.19+0.49초, 전체 보기 0.37초 이하).
- 검증하지 못한 것: 칠판 TV(Linux Chrome)에서의 동작과 `long-animation-frame` 지원 여부, 운영 DB의 권한 설정. 칠판 확인과 운영 SQL 적용 뒤 `docs/perf-queries.sql` 5번으로 수집 여부를 본다.
