# 라벨 "실제 출력" 확정 — 스풀러 방식 (2026-11-14)

## 문제
출력 버튼을 누르면 인쇄 창을 열기도 전에 박스 라벨 행·출력 이력이 기록됐다. 인쇄 창을 취소하거나 프린터가 못 뽑아도 "출력"으로 보였다.
브라우저(`afterprint`)는 취소·무소음 인쇄에서도 똑같이 발생해서 실제 출력 판정에 쓸 수 없다.

## 결정 (사용자 확정: 스풀러 방식을 전제로 진행, 프린터 PC 실험은 못 함)
- 프린터가 연결된 Windows PC에 PowerShell 에이전트를 예약 작업으로 두고, 인쇄 완료 이벤트(PrintService 307)에서 우리 작업을 찾아 서버에 알린다.
- 작업 연결: 출력할 때 `label_print_jobs` 행을 만들고 인쇄 창의 **문서 제목을 `AGE-LABEL-<작업 id>`**로 바꿔 인쇄한다(Chrome은 문서 제목을 인쇄 작업 이름으로 쓴다고 알려져 있다 — 미확인).
- 서버 인증: Supabase 함수 `confirm_label_print(작업 id, 페이지 수, 비밀)` + 비밀의 sha256 해시(`label_agent_keys`, 정책 없음). 에이전트는 anon 키로 호출한다. service role 키는 쓰지 않는다(AGENTS.md 규칙 유지).
- 확정 시점에야 박스 라벨 행(`box_labels`)·출력 이력(`box_label_events`)·출력한 박스 종류를 만든다. 바코드 번호는 날짜·업체번호·순번으로 정해지므로 확정 전에는 작업(`items`)에만 적어 둔다. 그래서 "라벨 행이 있으면 출력"으로 세는 기존 화면(대시보드·현황·상차 스캔)은 고치지 않아도 맞다.
- 페이지 수만큼만: 307의 인쇄 페이지 수 N → 작업 앞에서부터 N장만 출력으로 기록, 나머지는 미출력(상태 `partial`).
- 설정 스위치 `labelConfirmMode`(`button` 기본 / `spooler`). 실험을 못 했으므로 기본은 예전 동작이다. 호환 레이어가 아니라 "검증 전 안전 스위치"다 — 프린터 PC에서 검증이 끝나면 `button` 경로 삭제를 이슈로 남긴다.
- 화면: 확정 대기 중인 박스는 "출력 확인 중"(30분까지, 이후 미출력으로 돌아가 다시 출력 가능), 5초마다 다시 읽고 확정되면 목록도 새로 읽는다. 일괄 출력은 확인 대기 중인 박스를 뺀다.

## 알려진 한계 · 미검증
- **가장 큰 미검증**: 용지 없음·라벨 걸림·커버 열림에서도 307이 찍혀 "인쇄됨"이 될 수 있다. 그러면 이 방식은 "스풀러가 프린터로 넘김"까지만 보증한다. 4B-2054L 드라이버가 양방향 통신·TrueEndOfJob을 지원하는지 모른다.
- 307의 속성 순서(문서 이름 [1], 프린터 [4], 페이지 수 [7])는 문서의 메시지 서식에서 읽었고 실제 이벤트로 확인하지 못했다.
- Chrome 인쇄 작업 이름이 페이지 제목과 같은지 Windows 큐에서 확인하지 못했다.
- 인쇄 로그(PrintService/Operational)는 기본이 꺼져 있다(설치 스크립트가 켠다, 관리자 권한).
- 에이전트가 안 돌면 라벨이 "출력 확인 중"에 머문다(30분 뒤 미출력). 스위치를 `button`으로 되돌리면 예전 동작.
- 에이전트 비밀의 해시를 아는 사람은 역으로 비밀을 알 수 없지만, 비밀을 아는 사람은 pending 작업을 확정할 수 있다(이 함수는 그 일만 한다).

## 검증 (프린터 PC에서, `scripts/label-agent/README.md`의 확인 순서)
정상 1장 → 라벨 뺀 상태 → 커버 연 상태 → 연속 3장 → 인쇄 창 취소. 결과를 여기에 적는다(아직 비어 있음).
