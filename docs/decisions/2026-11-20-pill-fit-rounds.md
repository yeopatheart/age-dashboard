# 주문 목록 칩 글자 맞춤을 라운드 방식으로 (2026-11-20)

## 문제
주문 목록이 처음 열릴 때와 메뉴에서 이동해 올 때 화면이 약 4초, 폰트 로드 직후 약 2초 멈췄다(서버 응답은 0.2~0.7초, 브라우저 렌더 10ms 이하).
JS 자체 프로파일러로 확인: 활성 5.8초 중 5.3초가 `dashboard-client.tsx`의 칩 글자 크기 맞춤 `useLayoutEffect` 한 함수였다.
칩마다 글자 단계를 한 단계씩 줄이며 "스타일 쓰기 → `scrollHeight` 읽기"를 번갈아 해서, 읽을 때마다 화면 전체 레이아웃이 다시 계산됐다(칩 수 × 단계 수).
2026-11-14에 "조건은 먼저 읽고 바뀐 칩만 다시 맞춘다"로 한 번 고쳤지만 칩 안쪽 반복은 그대로였다.
DB는 병목이 아니었다(앱 쿼리 평균 2~5ms, CPU 2~6%).

## 결정
`src/lib/pill-fit.ts`의 `fitInRounds`: 바뀐 칩 전부에 같은 단계를 쓰고 → 한 번에 읽고 → 아직 넘치는 칩만 다음 단계로 내린다. 강제 레이아웃은 칩 수 × 단계 수에서 단계 수 이하로 준다.
옵션 줄 내림 보정(`--pshift`)도 읽기를 전부 끝낸 뒤 쓴다.
바꾸지 않은 것: 맞추는 규칙·단계 표·맞추는 시점(처음 로드, 폰트 로드 후, 내용·폭 변경)·줄 높이·`monitor-rows` 규칙.
전제: 칩은 고정 폭 칸 안에 있고 높이가 `maxHeight`로 막혀 있어 서로 높이에 영향을 주지 않는다 → 칩마다 따로 맞춘 결과와 같다.

## 검증 (이 Mac, 운영 빌드, 테스트 DB 70줄 시드 + 긴 이름 추가분, 칩 249·229·478개)
- 수정 전후 모든 칩의 `--pq --pn --pl --po --pshift`·scrollHeight·clientWidth·옵션 offsetTop 해시: 모니터 1·모니터 2·전체 보기 모두 **동일**(1024×768, 1440×900 모두).
  글자가 줄어드는 단계와 `--pshift 0.6px`가 실제로 나오는 데이터로 확인했다(모든 칩이 첫 단계면 비교가 약하다).
- `text-clip-audit.js`: 모니터 1·2는 수정 전 빌드와 수치가 같다(잘림 27/40, 기준선 0/0, 세로 중앙 12/27 — 시드의 극단적으로 긴 글자 때문에 수정 전에도 나오는 값). 전체 보기는 기준선 0·세로 중앙 0(478칩), 잘림 점검은 시간 초과로 못 돌렸고 CSS 변수 해시가 같아 렌더가 같다.
- 화면 멈춤(LoAF): 전체 보기(칩 478개) 수정 전 10.6초 + 8.3초 → 수정 후 가장 긴 것 0.34초. 모니터 1은 0.84초·0.27초, 모니터 2는 1.06초·0.48초가 남는다(칩 맞춤 외 비용, 4단계에서 다룸).
- 주문 한 줄 변경: 다시 맞춰진 칩 1개, 긴 멈춤 없음.
- 단위 테스트: 칩마다 따로 맞춘 기준 구현과 무작위 500칩 결과 동일, 읽기 횟수 ≤ 단계 수.

## 남은 것
